# H31.1 Shared List/Table Migration Contract

Status: archived shared list/table migration contract for completed H31 baseline.

## Purpose

Record the implementation contract that `H31` established for list/table migration.

This task doc remains the active source of truth for the shared table/list baseline. It exists to keep `H31` from drifting into shell rework already owned by `H30`, form/workflow redesign owned by `H32`, or dashboard/summary redesign owned by `H33`, and to give `H32`-`H34` a stable table/list contract to inherit rather than re-decide.

`H31` is the list/table migration layer for the broader UI modernization wave. It builds on the shared shell, theme, and layout baseline established by `H30` and defines how primary list/table surfaces should migrate toward a ScholarDex-owned, Bootstrap 5-compatible, light/dark-capable table system.

## Current Baseline

- The shared shell, theme contract, and bounded content layout baseline are already established by `H30`.
- Runtime templates continue to consume frontend assets through `/assets/app.css` and `/assets/app.js`.
- Authored frontend changes still flow through `frontend/src/**` and the existing asset build pipeline.
- The migrated table/list baseline now lives in the shared table foundation under `frontend/src/**`, including shared table surfaces, lighter integrated filter panels on migrated fetch-driven pages, shared badge/identifier treatment, and shared pager/layout patterns.
- Primary shared/admin fetch-driven list pages and pure user table pages have already been migrated to the shared ScholarDex table contract.
- Runtime tables still widely use `table table-bordered`, occasional `thead-light`, and other Bootstrap 4-era table presentation patterns outside untouched or deferred surfaces.
- BS4 DataTables coupling is still present in the current runtime.
- Current DataTables runtime debt includes the `datatables.net-bs4` import in `frontend/src/app.js`.
- Current DataTables runtime debt also includes `src/main/resources/static/js/demo/datatables-demo.js`.
- Many templates still rely on `js-datatable` and related `data-datatable-*` flags.
- For touched H31 surfaces, BS4 DataTables styling and bordered Bootstrap 4 table presentation are retired as the intended UX baseline.
- Shared, admin, and user list surfaces are all in play for `H31`, but some mixed workflow/dashboard pages remain intentionally deferred to later tasks.

## Locked Direction

- ScholarDex-owned table/list patterns are the intended UX baseline for touched list/table surfaces.
- Bootstrap 5-compatible markup and styling direction apply to touched list/table work.
- Light and dark themes are supported presentation modes within one shared table/list system.
- BS4 DataTables styling is transitional debt, not the target presentation contract.
- `H31` should create one consistent table/list language across shared, admin, and user surfaces rather than preserving page-by-page table drift.
- `H31` builds on the H30 shell/theme baseline and does not revisit shell ownership or shared-shell composition decisions.
- `H32`-`H34` inherit the shared table/list vocabulary, DataTables-as-compatibility-only direction, and light/dark list/table baseline established by `H31`.

## In Scope

- Shared table/list foundation under `frontend/src/**`.
- Table shell, header treatment, cell spacing, row dividers, hover states, badges, identifier formatting, empty states, responsive overflow, and toolbar structure.
- Migration of primary shared/admin list surfaces to the shared ScholarDex table contract.
- Migration of primary user list surfaces to the same shared contract.
- Retirement of BS4 DataTables presentation dependency on touched surfaces, even if some enhancement behavior remains temporarily.
- Docs and verification alignment for the table/list baseline established by `H31`.

## Out Of Scope / Non-Goals

- No shell, sidebar, topbar, page-header, or theme-state work owned by `H30`.
- No form, workflow, modal, or tooltip redesign owned by `H32`.
- No dashboard, summary, or feedback redesign owned by `H33`.
- No final Bootstrap 4/SB Admin remnant cleanup outside touched table/list surfaces; that belongs to `H34`.
- No route-family ownership changes.
- No unrelated backend, API, persistence, or schema changes.
- No repo-wide one-shot migration of every table in the codebase before `H31` can land.

## Implementation Constraints

- Use the existing frontend asset pipeline and `/assets/app.css` + `/assets/app.js`.
- Inherit the `H30` theme contract, including `data-bs-theme` on the root element as the shared theme-state source of truth.
- Do not introduce new Bootstrap 4-only table markup or new jQuery-driven list behavior.
- Do not expand `js-datatable` usage to new pages during migration.
- Touched templates should converge on one shared table/list contract instead of page-local table systems.
- If DataTables behavior remains on a touched page temporarily, the visible list/table presentation must still be ScholarDex-owned rather than stock BS4 DataTables.
- Shared/admin surfaces and user surfaces remain separate migration slices under the same shared table/list foundation.
- Later tasks should treat the shared table/list class vocabulary, lighter filter panel pattern, primary table surface structure, and DataTables-compatibility-only direction as fixed inherited foundations unless a new active contract explicitly reopens them.

## Acceptance Evidence Targets

- `H31.2` establishes the shared table/list foundation.
- `H31.3` migrates primary shared/admin list surfaces.
- `H31.4` migrates primary user list surfaces.
- `H31.5` aligns docs and guardrails with the post-H31 baseline.
- Touched surfaces no longer treat BS4 DataTables styling or bordered-grid Bootstrap 4 tables as the intended UX baseline.
- Table/list migration covers empty states, badges, toolbar structure, filtering, and pagination treatment rather than only CSS changes on `<table>` elements.
- `H32` owns mixed workflow pages deferred from H31, including modal-heavy or table-plus-form surfaces.
- `H33` owns dashboards, summaries, and pages where table work intersects stat/summary redesign.
- `H34` owns remaining Bootstrap 4/DataTables remnant cleanup, accessibility, and final cross-theme consistency closeout.

## Verification Expectations

Minimum targeted verification for touched `H31` implementation slices:

- `npm run build`
- `npm run verify-assets`
- `npm run verify-template-assets`
- `npm run verify-route-guardrails`
- `npm run verify-ui-guardrails` only when touched list/table pages intersect the route/UI surfaces already protected by that script

Broader validation should continue to come from `docs/quality-gates.md` based on the exact touched area. This contract names the minimum targeted checks for list/table migration slices; `verify-ui-guardrails` remains a narrow conditional check, not a universal list/table command.
