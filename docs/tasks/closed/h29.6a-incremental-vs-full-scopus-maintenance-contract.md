# H29.6a Incremental-vs-Full Scopus Maintenance Contract

Status: archived contract lock for non-destructive Scopus incremental maintenance.

## Purpose

Lock the maintenance contract for Scopus flows before further implementation work under `H29.6`.

This slice is documentation-only. It records which behaviors are shared across full and incremental Scopus maintenance, which behaviors must diverge, and the current known violation that later slices must fix.

## Locked Direction

- Full initialization and full rebuild flows are allowed to use full-rescan, replace-style semantics.
- Upload-driven and scheduler-driven Scopus batches are incremental, replay-safe, batch-scoped flows.
- Incremental flows must be non-destructive outside the state they can fully reconstruct from current canonical truth.
- The upload-driven Scopus build path is the baseline for batch-scoped canonical behavior:
  - batch-scoped fact build
  - batch-scoped canonicalization
  - `useCheckpoint=false`
- Scheduler publication and citation updates must converge to the same incremental contract, not the full-rebuild contract.

## Maintenance Modes

| Mode | Input scope | Fact build scope | Canonicalization scope | Checkpoints | Reconcile links/edges | Projection behavior | Replace/delete allowed |
|---|---|---|---|---|---|---|---|
| Full initialization / full rebuild | Full corpus | Full corpus | Full corpus | Allowed | Allowed when explicitly requested by full maintenance flow | Full rebuild | Yes |
| Incremental upload build | Uploaded batch (`sourceBatchId`) | Batch-scoped | Batch-scoped | Disabled | Not part of the base upload submit action | None in build step | No |
| Incremental upload projection rebuild | Uploaded batch (`sourceBatchId`) | N/A | N/A | N/A | Not part of projection step | Batch-scoped projection refresh | No, unless the same step can fully reconstruct the deleted scope |
| Scheduler publication update | Scheduler batch id | Batch-scoped | Batch-scoped | Disabled | Only batch-scoped reconcile behavior when explicitly enabled later | Batch-scoped projection refresh | No, unless the same step can fully reconstruct the deleted scope |
| Scheduler citation update | Scheduler batch id | Batch-scoped | Batch-scoped | Disabled | Only batch-scoped reconcile behavior when explicitly enabled later | Batch-scoped projection refresh | No, unless the same step can fully reconstruct the deleted scope |

## Shared vs Separate Rules

### Safe To Share

- Replay-safe ingest through import events.
- Batch-scoped fact building keyed by `sourceBatchId`.
- Batch-scoped canonicalization with checkpoint resume disabled.
- Deterministic reuse of canonical facts, source links, edges, and OPEN conflicts on replay.
- Shared orchestration helpers that preserve the batch/full distinction instead of hiding it.

### Must Stay Separate

- Full projection replacement logic versus incremental graph refresh logic.
- Full-corpus checkpoint semantics versus isolated batch execution semantics.
- Destructive delete-and-reinsert behavior for full rebuilds versus non-destructive refresh behavior for incremental batches.

## Non-Destructive Incremental Rule

- Incremental upload and scheduler runs must not delete or overwrite projection rows outside the set they can fully reconstruct from current canonical truth in the same operation.
- For graph-style projections, especially citations, the delete scope must never be broader than the reinsert or refresh scope.
- Incremental maintenance must preserve previously visible citations, edges, and related projection state that are still valid in canonical storage but fall outside the current batch neighborhood.

## Current Known Violation

`ScopusProjectionBuilderService.rebuildViewsForBatch(...)` currently violates the incremental contract for citation projections:

- it deletes projected citation rows for publications touched by the batch when either endpoint is affected
- it reinserts only a narrower subset of canonical citation rows
- this can remove previously visible citations from PostgreSQL-backed UI/reporting flows after incremental upload or scheduler maintenance

This behavior is acceptable for a full rebuild pattern, but not for incremental batch maintenance.

## Acceptance Evidence Targets For Later Slices

- Scheduler-driven publication/citation batches process canonical records instead of skipping due to global checkpoint state.
- Incremental upload and scheduler projection maintenance do not remove previously visible citations that remain valid in canonical citation storage.
- Upload-driven Scopus flow remains batch-scoped and replay-safe.
- Full rebuild behavior remains available for explicit initialization/recovery operations.

- `H29.6c`: fix batch-scoped citation projection maintenance so it is non-destructive.
- `H29.6d`: separate full-rebuild projection semantics from incremental graph refresh semantics.
- `H29.6e`: add regression coverage for non-destructive incremental Scopus maintenance.
