# H32.1 Shared Form/Workflow Migration Contract

Status: archived shared form/workflow migration contract for completed H32 baseline.

## Purpose

Record the implementation contract for `H32`.

This slice is documentation-only. It exists to prevent `H32` from drifting into shell rework already owned by `H30`, list/table foundation work already owned by `H31`, or dashboard/summary redesign owned by `H33`.

`H32` is the form and workflow migration layer for the broader UI modernization wave. It builds on the shared shell, theme, layout, and table/list baseline established by `H30` and `H31` and defines how primary create/edit, modal-heavy, multi-step, and apply-style workflows should migrate toward a ScholarDex-owned, Bootstrap 5-compatible, light/dark-capable form system.

## Current Baseline

- The shared shell, theme contract, bounded content layout, and shared table/list baseline are already established by `H30` and `H31`.
- Runtime templates continue to consume frontend assets through `/assets/app.css` and `/assets/app.js`.
- Authored frontend changes still flow through `frontend/src/**` and the existing asset build pipeline.
- The shared workflow foundation now lives in `frontend/src/**` and provides the active presentation contract for form surfaces, section grouping, action bars, step shells, workflow control panels, and modal shells.
- Primary admin create/edit and modal-heavy workflows now use the shared ScholarDex workflow contract instead of relying on stacked SB Admin cards as their intended presentation.
- Primary user multi-step and apply-style workflows now use the same shared contract on pages such as `publications-add-step*` and `indicators-apply-*`.
- Bootstrap 4-era modal, tooltip, collapse, input-group, and dense card/form presentation patterns still exist on untouched or deferred workflow surfaces, but they are migration debt only.
- Dynamic admin edit flows may still retain some legacy behavior compatibility, but touched workflow surfaces no longer treat Bootstrap 4 modal/tooltip/input-group styling as the intended baseline.

## Locked Direction

- ScholarDex-owned form and workflow patterns are the intended UX baseline for touched create/edit and multi-step workflow surfaces.
- Bootstrap 5-compatible markup and behavior direction apply to touched form/workflow work.
- Light and dark themes are supported presentation modes within one shared form/workflow system.
- Bootstrap 4 modal, tooltip, collapse, and input-group presentation/interaction patterns are transitional debt, not the target contract.
- `H32` should create one consistent form/workflow language across admin and user surfaces rather than preserving page-by-page workflow drift.
- `H32` builds on the H30 shell/theme baseline and the H31 table/list baseline and does not revisit shell or shared list ownership decisions.
- `H33`-`H34` inherit the shared form/workflow vocabulary, modal/tooltip migration direction, migrated workflow examples, and light/dark workflow baseline established by `H32`.

## In Scope

- Shared form/workflow foundation under `frontend/src/**`.
- Label/input/help-text hierarchy, validation and error treatment, readonly presentation, action bars, section grouping, and step/progress framing.
- Migration of primary admin create/edit and modal-heavy workflow surfaces to the shared ScholarDex form/workflow contract.
- Migration of primary user multi-step and apply-style workflow surfaces to the same shared contract.
- Replacement or retirement of touched Bootstrap 4 modal/tooltip/input-group assumptions where those patterns conflict with the intended workflow baseline.
- Docs and verification alignment for the form/workflow baseline established by `H32`.

## Out Of Scope / Non-Goals

- No shell, sidebar, topbar, page-header, or theme-state work owned by `H30`.
- No shared table/list foundation work owned by `H31`.
- No dashboard, summary, or feedback redesign owned by `H33`.
- No final Bootstrap 4/SB Admin remnant cleanup outside touched form/workflow surfaces; that belongs to `H34`.
- No route-family ownership changes.
- No unrelated backend, API, persistence, or schema changes.
- No repo-wide one-shot rewrite of every form, modal, or workflow before `H32` can land.

## Implementation Constraints

- Use the existing frontend asset pipeline and `/assets/app.css` + `/assets/app.js`.
- Inherit the `H30` theme contract, including `data-bs-theme` on the root element as the shared theme-state source of truth.
- Inherit the `H31` table/list contract where workflow pages intersect migrated tables.
- Do not introduce new Bootstrap 4-only form, modal, tooltip, collapse, or input-group patterns.
- Do not introduce new jQuery-driven workflow behavior as the intended steady-state interaction model.
- Touched templates should converge on one shared form/workflow contract instead of page-local form systems.
- If Bootstrap-era or jQuery-era workflow behavior remains on a touched page temporarily, the visible form/workflow presentation must still be ScholarDex-owned rather than stock Bootstrap 4.
- Admin create/edit surfaces and user multi-step/apply surfaces remain separate migration slices under the same shared form/workflow foundation.

## Acceptance Evidence Targets

- `H32.2` establishes the shared form/workflow foundation.
- `H32.3` migrates primary admin create/edit and modal-heavy workflows.
- `H32.4` migrates primary user multi-step and apply-style workflows.
- `H32.5` aligns docs and guardrails with the post-H32 baseline.
- Touched surfaces no longer treat Bootstrap 4 modal/tooltip/input-group patterns as the intended UX baseline.
- Form/workflow migration covers labels, help text, validation, readonly treatment, action structure, and step orientation rather than only CSS changes on form controls.
- `H33` owns dashboards, summaries, and pages where workflow work intersects stat/summary redesign, including mixed or feedback-heavy surfaces deferred from `H32`.
- `H34` owns remaining Bootstrap 4/SB Admin remnant cleanup, accessibility, and final cross-theme consistency closeout for untouched workflow surfaces.

## Verification Expectations

Minimum targeted verification for touched `H32` implementation slices:

- `npm run build`
- `npm run verify-assets`
- `npm run verify-template-assets`
- `npm run verify-route-guardrails`
- `npm run verify-ui-guardrails` only when touched workflow pages intersect the route/UI surfaces already protected by that script

Broader validation should continue to come from `docs/quality-gates.md` based on the exact touched area. This contract names the minimum targeted checks for form/workflow migration slices; `verify-ui-guardrails` remains a narrow conditional check, not a universal form/workflow command.
