# H50.2 Export — xlsx for `Fisa-verificare_Informatica_2016`

**Status:** Planning
**Created:** 2026-05-13
**Parent:** [H50](../active/h50-individual-report-export-import.md)

## Purpose

Wire end-to-end **xlsx export** of a `UserIndividualReportRun` for the one existing individual-report type, using `data/templates/Fisa-verificare_Informatica_2016.xlsx` as a stamped template. Establish the binding-file pattern so adding more report types in H50.5 is a config change, not new Java.

## Scope (in)

- Bundled template resource: `src/main/resources/report-templates/informatica-2016/template.xlsx` (copied from `data/templates/`).
- Bundled binding resource: `src/main/resources/report-templates/informatica-2016/binding.json`.
- A `ReportTypeImportSupport` impl for `reportTypeKey = "informatica-2016"` that implements **render only** (parse/reconcile/commit return `UnsupportedOperationException` until H50.3).
- A generic `TemplateXlsxRenderer` driven by the binding, used by the above impl.
- `IndividualReport.indicatorRolesByIndicatorId: Map<String,String>` field (additive Mongo, no migration).
- `IndividualReport.reportTypeKey: String` field (additive Mongo) — the binding lookup key.
- Admin report-edit UI: read-only display of `reportTypeKey` if set, plus a per-indicator role-key dropdown sourced from the binding's declared roles.
- Workspace UI: an "Export to xlsx" button on the report-run dashboard that posts to a new endpoint and streams the workbook.

## Scope (out — explicitly)

- Import / dry-run reconciliation (H50.3).
- docx export (H50.4).
- Other report types (H50.5).
- Editing or uploading custom templates from the admin UI (deferred indefinitely).
- The `Centralizator!D25-27` h-index cells: left blank for user to fill, per the parent-task decision.

- `publication.*`, `citation.*`, `activity.*` — drawn from the per-row projector for that role's data source.

Write-policy vocabulary (`policy` string): `WRITE` | `SKIP_FORMULA` | `WRITE_SCORE` | `MANUAL`.

### 2. Data sources (per indicator-role)

Reuses existing facade plumbing:

- `journal-publications`, `conference-publications`:
  - Pull `findConfirmedPublicationsForScoring(userEmail)` → `List<ScholardexPublicationView>`.
  - Join forums via `findForumsByIds(...)` → `Map<forumId, ScholardexForumView>`.
  - Filter to publications scored by the bound indicator using the indicator's rawGraph `scores` map keys (titles in scope) — same logic the dashboard's `/indicator/{id}/detail` endpoint uses.
  - Split journal vs conference by forum type (or by which indicator-role the publication belongs to — already encoded in the bound indicator).
- `citations-per-publication`:
  - Use the citation indicator's rawGraph: nested `Map<pubTitle, Map<citingKey, Score>>`.
  - For each top-level pub, generate one tile; for each inner citation, generate one row.
  - Join citing publications back to `ScholardexPublicationView` / `ScholardexForumView` for the richer columns.
- `activities-perspectiva-d`:
  - Use the umbrella indicator's rawGraph `outputMode = "activities"`: `scores: Map<activityKey, Score>` + `activities: Map<...>` for labels + per-activity `details`.
  - Resolve which sub-block to write each row into via `Indicator.activity` (DBRef) → match the binding's `activityName`. Indicators not in any sub-block are dropped with a logged warning.
  - **Write `K` (score)** for each data row — this is the lone column where we override what would otherwise be a user-entered value. The TOTAL row's K stays formula-driven.

A small **row projector** per data type (`PublicationRowProjector`, `CitationRowProjector`, `ActivityRowProjector`) materializes `Map<String, Object>` rows keyed by the source vocabulary (`publication.title`, `publication.forumCategoryLetter`, …). Reuses the existing `handlePublicationsWorkbook`/`handleCitationsWorkbook` field-extraction logic where possible — opportunity to extract shared helpers, but only if the refactor stays local. If extraction balloons, defer it to a follow-up.

### 3. Generic `TemplateXlsxRenderer`

Single class. Inputs: binding + `Map<roleKey, List<Map<String, Object>>>` (rows per role) + scalar value lookup. Output: `byte[]`.

Loads the template via `WorkbookFactory.create(InputStream)`. Per role kind:

- **`FIXED_TABLE`** — iterate rows up to `maxRows`. For each column, look up the policy: `WRITE` calls `setCellValue` with type inference; `SKIP_FORMULA` leaves the existing cell alone; `WRITE_SCORE` same as `WRITE` but typed as `double`. Overflow logs a warning and truncates.
- **`STACKED_BLOCKS`** — for each block, resolve which rows belong to it (by `activityName` match), then write into the block's `firstDataRow` (assumed single-row per block; expand if `activity.score` rows multiply — the template gives one row per block, which is the schema's contract). The total row's K column is left as-is.
- **`TILED_SHEETS`** — for each tile:
  1. `Workbook.cloneSheet(templateSheetIndex)` → new sheet at end.
  2. `Workbook.setSheetName(newIdx, sheetNameTemplate.format(index))`.
  3. Write per-tile scalar (`C5` title, `J21` author count).
  4. Write inner rows via the same `FIXED_TABLE` logic.

  After all tiles are cloned, delete the original `C-Citari-TPL` sheet (or hide it — see open question). Then regenerate the summary cells in `summarySheet` via `summaryFormulaRegeneration`: for each `{cell, tileCell, rule}` entry, build the formula `=SUM('Citari-01'!I22,'Citari-02'!I22,...)` and `setCellFormula(...)`.

- **Scalar cells** with `policy = MANUAL` are no-ops (cell is left alone — likely already blank or pre-filled in the template).

### 4. Wiring

- `Informatica2016ReportTypeImportSupport extends ReportTypeImportSupport` — `reportTypeKey() = "informatica-2016"`; `supportedExportFormats() = {XLSX}`; `supportedImportFormats() = {}`; `render(...)` delegates to `TemplateXlsxRenderer` with the bundled binding; `parse`/`reconcile`/`commit` throw `UnsupportedOperationException`.
- Registry collects this bean via the existing `ReportImportRegistry`.
- New controller endpoint: `GET /user/evaluation/export?report={reportId}&format=xlsx` → looks up the `UserIndividualReportRun` for the current user, resolves the `IndividualReport.reportTypeKey`, asks the registry for support, builds the snapshot, renders, streams.
- Snapshot building: a new `ReportInstanceSnapshotBuilder` collects per-role data via the data sources above, populates `ReportInstanceSnapshot.items` with concrete `SnapshotItem` subtypes (introduced in this slice): `PublicationSnapshotItem`, `CitationSnapshotItem`, `ActivitySnapshotItem`. These are simple `@Data` records with the projector field names — keeps the snapshot human-readable for the JSON form we'll need in H50.3.

### 5. Admin UI — minimal touch

[`AdminIndividualReportsController`](../../../src/main/java/ro/uvt/pokedex/core/view/AdminIndividualReportsController.java) / [`edit-individualReport.html`](../../../src/main/resources/templates/admin/edit-individualReport.html):

- Read-write `reportTypeKey` text field (free-form String for now; validation against registered keys is enough).
- Per-indicator role-key picker: dropdown sourced from `registry.require(reportTypeKey).declaredRoles()`. Saves into `indicatorRolesByIndicatorId`. If `reportTypeKey` is blank or unregistered, hide the picker.

Add a `declaredRoles()` method to `ReportTypeImportSupport` returning the binding's role keys (lets the admin UI populate dropdowns without reading the binding file directly).

### 6. Workspace UI

`individual-report-view.html`: add an "Export to Excel" button in the page toolbar, visible only when `report.reportTypeKey` is set and the registry has a support for it. Link target = the new endpoint. Existing per-indicator "Export indicator to Excel" button at the row level stays as-is.

## Open Questions

1. **Cleanup of the `C-Citari-TPL` sheet after tiling**: delete it or hide it? Deleting is cleaner output; hiding is safer if the binding's summary-formula regeneration references it accidentally. Recommend **delete**.
2. **Sheet name collisions**: if the user re-runs export, sheets like `Citari-01` would already exist when we run a tile loop on a re-opened workbook — non-issue since we always start fresh from the bundled template. Documenting it so we don't accidentally introduce caching later.
3. **`citationCount` / `citationPoints` columns on B-Reviste / B-Conferinte**: the template has these as **manual** input columns (no formula on K/L of journal rows; L drives the SUMs). The publications indicator's rawGraph carries `authorScore`/`forumScore` but not a citation count per publication — that comes from the citations indicator. Decision: leave columns `K`/`L` blank in H50.2 (write `MANUAL` policy), then revisit in H50.5 once we know whether the citations indicator can be joined to its publications for citation counts. Marked `WRITE` with source `publication.citationCount` in the draft above; change to `MANUAL` if no per-pub count is available.
4. **Activity row count per sub-block**: each block in the template has exactly one data row. Real users typically have multiple activities per category. Two options: (a) for H50.2, write only the highest-scoring activity per block and log a warning if there are more; (b) preemptively insert rows when there are >1. Option (a) is the minimal-diff path; option (b) means dealing with formula range shifts. Recommend **(a) for H50.2**, schedule (b) as part of H50.5 polish.

## Proposed Slicing

- **H50.2.a** — Binding format + loader + validation. `TemplateXlsxRenderer` skeleton with `FIXED_TABLE` only. Render journal-publications end-to-end against a hand-crafted snapshot fixture.
- **H50.2.b** — `STACKED_BLOCKS` support. Render activities-perspectiva-d. Activity→sub-block resolution via DBRef.
- **H50.2.c** — `TILED_SHEETS` support, including sheet clone + summary formula regeneration. Render citations-per-publication.
- **H50.2.d** — Wiring: `Informatica2016ReportTypeImportSupport`, snapshot builder, controller endpoint, workspace button.
- **H50.2.e** — Admin UI for `reportTypeKey` + per-indicator role mapping.

## Verification

- Unit: binding-loader validates referenced sheets/cells against bundled template; rejects unknown sources/policies.
- Unit: `TemplateXlsxRenderer` per kind — fixed table truncation, stacked block write, tile cloning + formula regeneration. Use a tiny synthetic workbook fixture to isolate POI logic from the real template.
- Integration: render the real template with a seeded run for one researcher; open the resulting file in LibreOffice headless (`soffice --convert-to xlsx --calc-pdf-export-recompute=...`) and assert recomputed totals on `Centralizator!D7`, `D11`, `D15`, `D19` match expected values for the fixture. If headless office is too heavy, fall back to manual smoke + recomputing key formulas in Java via POI's `FormulaEvaluator`.
- Manual: open in Excel/LibreOffice, verify formulas re-evaluate, no `#REF!` or `#NAME?`, citation tile sheets render correctly, activity scores show in K column.
- Security: no path traversal in `templateResource` (classpath-only); generated workbook size cap before streaming.

## Risks

- **POI `cloneSheet` quirks** — known to misbehave with merged regions, conditional formatting, and named ranges that reference the source sheet. Worth a small spike in H50.2.c before committing to the design; fallback is repeating the table vertically inside `C-Citari-centralizare` (your original "stacked in one sheet" suggestion).
- **Formula regeneration correctness** — the summary block formulas need exact range syntax. Cross-sheet 3D references aren't supported by POI for all functions; we may need explicit `SUM('Citari-01'!I22, 'Citari-02'!I22, …)` rather than `SUM('Citari-01:Citari-N'!I22)`. The binding's `SUM_OVER_TILES` rule explicitly assumes the former.
- **Category letter mapping** — `coreRankingEquivalent` confirmed to produce `AA`/`A`/`B`/`C`/`D` (per parent task Q4). If empty/null, write empty string (template's IF formula falls through to `0`).
